# Plan: README CLI-table automation + Upgrade section

Status: implemented
Depends on: 001--initial-implementation (complete)

## Goal

1. Make the `## Available CLIs` table in `README.md` a **generated artifact**,
   regenerated by `script/update.py` on the same runs that regenerate the
   formulas, so the "Latest" column can never drift from the formulas that are
   actually committed.
2. Add a hand-written `## Upgrade` section to `README.md`, directly after
   `## Install`.

Non-goals: changing formula generation, apps.json app list, or the workflow
schedule/permissions model.

## 1. Generated README table (script/update.py)

### Markers (one-time hand edit of README.md)

Wrap the existing `## Available CLIs` table in explicit markers so the
generator owns exactly the table, and humans own the surrounding prose:

```md
## Available CLIs

<!-- generated:available-clis:start -->
| Formula | App | Latest |
|---|---|---|
| … generated rows …
<!-- generated:available-clis:end -->
```

Rules:
- If a marker is missing or the markers are not properly ordered, the script
  **fails loudly** and touches nothing (fail-closed, same spirit as §3 of the
  constitution). It must never guess where to inject the table.
- Everything between the markers is generator output; everything outside them
  stays hand-edited and is never rewritten by the script.

### Data source

Reuse the release info (`{app, org, version, tag}`) already fetched per app by
`fetch_release` — no extra API calls.

New per-app metadata in `apps.json` (single source of truth per constitution
§2), because the README table's display name and tagline ("interface design &
prototyping") are distinct from the formula `desc` strings:

```json
"readme": {
  "figcraft":   { "display_name": "FigCraft",   "tagline": "interface design & prototyping" },
  "deckcraft":  { "display_name": "DeckCraft",  "tagline": "presentations & slideshows" }
  …
}
```

- Every app listed in `apps` must have a `readme` entry; a missing/incomplete
  entry fails loudly for that app (mirrors the `descriptions` handling).
- Row order = `apps` order (figcraft first, matching today's table).

### Rendering rules

- Row shape is unchanged: `` | `<app>-cli` | [<Display>](https://github.com/storytold/<app>) — <tagline> | <version> | ``.
- A version in the table **must** equal the version in the corresponding
  regenerated `Formula/<app>-cli.rb` — guaranteed by construction since both
  come from the same `info` dict in the same run.

### Fail-closed semantics (constitution §2/§3 alignment)

- Per-app failures already abort the run (`main` returns 1 → CI stops before
  the commit step). Within the README step: the section is rewritten only if
  **all** apps succeeded, so the README can never advertise a version that has
  no formula (and vice versa).
- Idempotency: rendering the table from unchanged data produces zero diff
  (constitution §2). The table is fully deterministic: no timestamps, no
  sorted-by-date surprises, stable column order.

### `--check` mode

`python3 script/update.py --check` additionally renders the README section and
compares it to what's committed between the markers; drift → exit 1. CI now
covers both artifacts with one gate (constitution §4).

## 2. `## Upgrade` section (hand-written, static)

Inserted immediately after `## Install`, before `## Available CLIs`:

```md
## Upgrade

```sh
brew update
brew upgrade
```

Or upgrade a single CLI:

```sh
brew upgrade 01Joseph-Hwang10/artcraft/deckcraft-cli
```

Because every formula is regenerated in lockstep with the upstream release
(version comes from the release asset filename), `brew upgrade` always lands
the CLI on the exact version of the latest app release — never a stale or
mismatched build.
```

This section is **not** generated and lives outside the markers.

## 3. Workflow (.github/workflows/update.yml)

- `pull_request.paths`: add `README.md` so hand-edits to the README also run
  the drift check.
- Regenerate + commit steps: extend to `git add Formula README.md` (the commit
  message stays mechanical; optionally mention README in the message).
- No new triggers, no new permissions — the existing schedule/dispatch/PR model
  and §7 push rules are unchanged.

## 4. Constitution amendments

Minimal, in-place (no renumbering):

- **§2 (Generated, not hand-edited)**: extend the rule to the README's
  generated region — the `## Available CLIs` table between the markers is a
  build artifact of `script/update.py`; fix the generator, then regenerate.
- **§4 (Integrity gates)**: the CI drift check also covers the README
  generated region.
- **§7 (Automation safety)**: CI may additionally commit the regenerated
  README table (still purely mechanical output); any change to the table's
  row shape, markers, or `apps.json` `readme` metadata is a reviewed PR.

Full text of the amendments is applied to `specs/constitution.md` as part of
this change.

## 5. Implementation steps

1. Amend `specs/constitution.md` (§2, §4, §7 as above).
2. Add `readme` metadata (display name + tagline) for all 13 apps to
   `apps.json`.
3. Add markers around the `## Available CLIs` table in `README.md`; add the
   hand-written `## Upgrade` section after `## Install`.
4. Extend `script/update.py`: render README section, fail-closed marker
   validation, write only when all apps succeed, include README in `--check`.
5. Extend `.github/workflows/update.yml` (paths + `git add README.md`).
6. Verify locally:
   - `python3 script/update.py` twice → second run is a zero diff (idempotent).
   - `python3 script/update.py --check` → exit 0 on committed state; exit 1
     after perturbing a row or a formula version.
   - Corrupt/remove a marker → script fails loudly, nothing written.
   - `brew audit --strict --formula` unaffected (no formula template change),
     but re-run once as a regression gate (constitution §4).

## 6. Risks / notes

- Table text changes (e.g. new taglines) are a visible diff to users —
  acceptable; the row shape is frozen in this plan.
- GitHub-flavored tables don't support literal `|` in cells; taglines use `&`
  (`design & prototyping`), which is safe — validation should reject `|` in
  `tagline` to fail closed early.
- The `Verify:` line below the table stays hand-edited **outside** the markers,
  with generalized wording ("prints the installed version, matching the latest
  upstream release") instead of an exact version example, so it never goes
  stale as releases advance.
